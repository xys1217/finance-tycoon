## 每日信号机制

### 调度

| 项 | 值 |
|---|---|
| 时间 | 工作日 **08:30**（Asia/Shanghai） |
| 通道 | 项目定时任务「每日 8:30 生成 A 股交易信号」（id 7025967） |
| 脚本 | `web/run_daily_signal.sh`（非交易日自动跳过，失败重试一次） |
| 耗时 | 首次约 95 秒（641 只 K 线），命中缓存约 7 秒 |

沙箱未装 cron（`apt-get install cron` 无安装源），且**沙箱闲置会休眠**，
所以主通道走平台级定时任务。若要部署到自己的服务器：

```cron
30 8 * * 1-5 /workspace/web/run_daily_signal.sh >> /workspace/logs/daily_signal.log 2>&1
```

### 两轨输出（关键设计）

| 轨道 | 内容 | 是否执行 |
|---|---|---|
| **执行指令** | 按调仓日历判定。非调仓日 → 「维持上期持仓，不换股」 | ✅ 真金白银 |
| **每日观察** | 每天重算的六因子 / 12-1 动量排名 | ❌ 仅供观察 |

**为什么不每天换股**：个股腿按 v5 定案是**季频调仓**（1/4/7/10 月首个交易日）。
天天换手要付佣金 0.025% + 滑点 0.1% + 印花税 0.05%，而 v5 的回测收益正是
**按季频换手**验证出来的。日频调仓是另一个没有回测支撑的策略。

### 调仓日历

- 个股腿：**季频**，1/4/7/10 月首个交易日
- ETF 腿：**月频**，每月首个交易日
- 交易日来自新浪交易日历（`ak.tool_trade_date_hist_sina`），覆盖到 2026-12-31

### 三条口径铁律

1. **打分与闸门一律用 `bar_date`**（最后一个完整交易日收盘），绝不能用 `sig_date`。
   盘中运行时最后一根 K 线是未完成的，必须剔除，否则三道闸门因盘中价失真而
   **静默失效**，高价股（江波龙 369 元、中际旭创 859 元）会混进 top3。
2. **剔除无权限板块**：科创板 688/689、北交所 4xx/8xx、B 股 9xx；个股股价 ≤ 120 元。
3. **去重靠买入循环里的 `used_codes`**，不能用 `[c for c in hot if c not in stock]`。

### 数据新鲜度自检

`data_freshness` 字段报告 `stale` 与 `bars_behind`，**bar_date 落后会在页面顶部弹红色告警**，
绝不让旧因子静默生效。

**上游日线数据有延迟**：实测收盘后 4 分钟，`ak.stock_zh_a_daily` 最后一根仍是上一交易日
（通常要 15:30 之后才更新）。这不是代码问题，脚本会持续告警直到数据到位。

缓存新鲜度**按 bar_date 判定，不按文件修改时间**，且 manifest 记录的是**实际数据**
的 bar_date 而非期望值。这里踩过两个坑：

1. **按 mtime 判定**：早上 8:30 缓存 bar=09-02，当晚 20:00 再跑，文件才 11.5 小时
   「新鲜」，但 09-03 已收盘 → 拿旧因子给 09-04 下单。
2. **manifest 写期望值**：上游延迟时 manifest 记成 want_bar(09-03)，
   明早重跑 want_bar 正好也是 09-03 → **缓存永久命中，永远拿不到 09-02 之后的新数据**，
   重跑多少次都一样。

另外给上游延迟加了 30 分钟宽限（`attempted_for` 字段）：这段时间内不重复拉，
避免每次重跑白等 90 秒，但 stale 告警照常触发。`written_at` 只在**真的拉取过**时更新，
否则宽限期会被无限续期。

## 第四轮检查（2026-09-03 22:20 起）—— 换方法后挖出真东西

前三轮每次「确认没问题」之后又被发现新问题，根因不是不够仔细，而是
**检查方法本身有缺陷**：一直在做确认式检查（验证我认为对的地方），
而不是去找「我没想到会错的地方」。这轮换了三件事：

1. **静态分析**：pyflakes + 跨模块返回值/解包一致性（此前一次都没跑过）
2. **参数矩阵**：每个端点 × 正常/缺失/非法/边界参数穷举，不挑着测
3. **真点按钮**：前三轮只验证页面渲染，从没点过任何按钮

结果挖到 5 个此前完全没发现的问题。

### 🔴 最重要的一个：模拟盘四个按钮从加上那天起就是坏的

```javascript
const J = async u => (await fetch(u)).json();      // 只有一个形参
// 调用处：
J("/api/paper/order", {method:"POST", body:...})   // 第二个实参被静默丢弃
```

`J` 只有一个形参，`{method:"POST"}` 被丢掉，实际发出的是 **GET**，
而 `/api/paper/order|plan|reset` 只接受 POST → 一律 404 → 前端 catch 到
异常但不说人话 → **按钮点了没反应**。

受影响：**买入、卖出、一键跟单、重置**——模拟盘的全部核心交互。
前三轮没发现，是因为只测了页面渲染和后端 API，从没用前端真点过按钮。

修复：`J` 透传 `opt`，并在服务端返回非 JSON 时抛出可读的
`HTTP 404 Not Found — ...` 而不是 `Unexpected token <`。

### 本轮修复清单

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | `J()` 丢弃第二个参数 | 模拟盘 4 个按钮全部失效 | 透传 `opt` + 错误信息可读化 |
| 2 | `POST /api/positions` 传数组 → 500 | 接口直接崩，前端只看到 HTML 错误页 | 类型校验，返回 400 + 明确提示；顺带原子写 |
| 3 | 重复点「一键跟单」= 无脑加仓 | 现金 13.4% → 2.0%，仓位翻倍 | 改成**幂等**：只补到目标股数，够就不买 |
| 4 | `mkstemp` 产物权限 0600 | 同机同用户没事，换用户/容器就读不到 | 写完 `chmod 0644` |
| 5 | 离线版在 `file://` 下仍 fetch | 控制台刷 `URL scheme "file" is not supported` | `file:` 协议直接用内嵌数据，不发请求 |

另外清理了 5 处 pyflakes 告警（未使用导入与死变量），
并修好 `build_static.py` 里**写死锚点**的顺序自检（J 改签名后它恒 FAIL，等于失效）。

### 一个必须记住的教训：检查工具本身要做过负向测试

第一版 `arities_check.py` 跑出「干净 ✓」，但**它是瞎的**——
只认 `return (a,b,c)` 字面量，而 `sig_plan()` 是
`out.append((...)); return out`，表里根本没有这个函数，
于是所有针对它的检查全部静默失效。

补上 `append`/`yield` 模式后重做**双重负向测试**才确认有效：

| 注入的 bug | 是否被抓到 |
|---|---|
| `server.py` 直接调用点解包 5→4 | ✅ `server.py:153 列表推导解包 sig_plan() → 4 个变量，但该函数返回长度 [5]` |
| `engine.py` 先赋值再遍历解包 5→4 | ✅ `engine.py:349 遍历 plan（来自 sig_plan()）解包 4 个变量` |

修复后收集到的函数从 8 个增加到 20 个（append 模式补上了）。

## v5 定案配置

| 项 | 值 |
|---|---|
| 总本金 | 200,000 元 |
| ETF 腿 | 12 只，月频调仓，合计 58% |
| 个股腿 | 季频调仓（1/4/7/10 月首个交易日） |
| ├ 防御仓 | 4 只 × 6.5% = 26%，修正六因子 |
| └ 热点仓 | 1 只 × 4% = 4%，12-1 动量 + 不追高三闸门 |
| 个股止损 | −25%（仅防黑天鹅） |
| 个股股价 | ≤ 120 元 |

### 关键公式

**防御仓 修正六因子**
```
(z(价值BP) + z(大市值) + z(12-1动量) + z(1月反转) − z(60日波动) + z(流动性)) / 6
```
小市值方向已反转。沪深300 池内 SMB 的 IC = −0.028~−0.051、t = −3.2~−6.9，
是负 alpha，写成 −z_size 等于常年倒着下注。

**热点仓 12-1 动量** = 近12个月收益 − 最近1个月收益（刻意剔掉最近一个月，
避开 A 股短期反转陷阱）

**三道不追高闸门**：近20日涨幅 ≤ +15% / 现价距52周高 ≤ 95% / CMF(20) ≥ −0.15

### 可执行口径

整手约束 100 股/份 + 佣金 0.025%（最低 5 元）+ 滑点 0.1%（买上浮卖下浮）
+ 卖出印花税 0.05%（ETF 免）。

**ETF 腿两轮分配**：第一轮按目标权重买，第二轮把剩余现金补给「目标金额买不满
1 手」的标的。十年国债 ETF 135.8 元、国债 ETF 118.2 元，1 手要 1.36 万 / 1.18 万，
而单只预算只有 9,667 元 —— 不补位就白白少 9.66% 仓位。修之前投入只有 74.2%，
修完 86.9%（与 v5 原始信号的 88% 吻合）。

## 第三轮检查记录（2026-09-03 17:30 起）—— 抓到一个会亏钱的 bug

前面两轮都在查「信号算得对不对」，这轮把手伸到了**模拟盘跟单链路**，结果挖出
两个必须修的问题。

### Bug A：一键跟单会把某只股票灌成 4 倍重仓

**现象**：跟单 17 只后现金只剩 **1,430 元（0.7%）**，而信号规划留的是
**26,840 元（13.4%）**。三环集团 300408 目标 5.55%，实买 **400 股 44,419 元（22%）**。

**根因**（两个问题叠加）：

| # | 问题 | 说明 |
|---|---|---|
| A1 | `sig_plan` 用 `weight_actual` 反推预算 | `weight_actual` 是**已扣掉成本之后**的实际占比，再乘本金当预算等于自我收紧。三环预算 13,000 被算成 11,100，而实时价 100 股要 11,105 —— **差 5 元买不起 1 手** |
| A2 | 第二轮现金补位无差别生效、无上限 | 补位逻辑本是为「国债 ETF 单价 135/118 元、单只预算 9,667 买不起 1 手」设计的，却对**任何**买不起的标的都生效，`share = 全部剩余现金 / len(pending)`。个股一旦买不起，就被灌进全部剩余现金 |

**修复**：

1. `sig_plan` 改取信号原生的 `budget`（防御仓 13,000 / 热点仓 8,000 / ETF 9,667），
   并带上信号算好的 `shares`
2. 新增 `_buy_for_plan()`：优先照信号股数下单，实时价偏高时**逐手递减**到预算内
   （2% 容差），不再直接判失败
3. 第二轮补位**只对 ETF 腿**生效，单只上限 `预算 × 1.6`，账户总投入上限 `本金 × 95%`；
   个股腿不补位，宁可不买也不超配

**修复后**：跟单 17 只与信号股数 **17/17 完全一致**，现金 26,839.71（13.44%），
与信号规划的 26,839.92（13.42%）对齐。
